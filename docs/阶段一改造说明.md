# wwvllm 阶段一：统一调度与异步推理改造说明

## 1. 文档范围和版本

本文对比本仓库的两个 Git 版本：

- 原始版本：`57ac1cd`（Initial commit）。
- 修改后版本：`e0c3da7`（Add unified scheduling and asynchronous inference）。
- 比较对象是本仓库的实现，不是未经固定版本的上游 nano-vLLM。完整差异可通过 `git diff 57ac1cd e0c3da7` 查看。

每一阶段的代码块摘自对应版本，部分代码块省略了与解释无关的语句；标注“示意”的代码不是完整源码。实际效果分为**理论预期**、**正确性验证**和**实测性能**。目前没有同条件的原始版本性能基线，因此不能计算性能提升百分比。

整体数据流：

```text
客户端 submit → 请求队列 → Scheduler → SchedulerOutput
    → KV Block 预留 → ModelRunner 构造批次 → Attention / LM Head
    → Scheduler.postprocess → token 流 / Future / 资源释放
```

## 2. 阶段一：统一请求状态和调度输出

**修改点与文件**：`engine/sequence.py` 增加请求 ID、时间戳、抢占次数和取消/失败状态；新增 `engine/scheduler_output.py` 描述每个请求本轮计算量、执行模式和是否采样；`engine/llm_engine.py` 接收新的调度输出。`num_cached_tokens` 沿用现有字段，表示已完成前向计算并具有有效 KV 的 token 数。

### 原始策略及理论

原版用 `WAITING`、`RUNNING`、`FINISHED` 表达生命周期，用 `num_tokens`、`num_cached_tokens`、`num_scheduled_tokens` 分别记录当前已知 token、已计算 token、本轮 token。`schedule()` 返回 `(seqs, is_prefill)`，整个批次只有一个布尔类型，无法表达同一轮中部分请求是 Prefill、部分是 Decode。

原始代码（`engine/sequence.py` 和 `engine/scheduler.py` 节选）：

```python
class SequenceStatus(Enum):
    WAITING = auto()
    RUNNING = auto()
    FINISHED = auto()

self.num_cached_tokens = 0
self.num_scheduled_tokens = 0
self.is_prefill = True

# schedule() 返回值示例
return scheduled_seqs, True  # 整个批次都是 prefill
```

### 修改后策略及理论

统一的请求级输出使调度器只负责决定每个请求计算多少 token，执行层再根据整个批次组织计算。关键不变量是 `0 <= num_cached_tokens <= num_tokens`；新采样 token 加入 `token_ids` 后尚未前向计算，不能立即计入 `num_cached_tokens`。`should_sample` 只有在本轮计算到当前已知 token 的末尾时为真，因此中间 chunk 不生成 token。

修改后代码（`engine/scheduler_output.py`）：

```python
@dataclass
class ScheduledRequest:
    seq: object
    num_scheduled_tokens: int
    mode: ExecutionMode
    should_sample: bool

@dataclass
class SchedulerOutput:
    scheduled: list[ScheduledRequest]
    num_scheduled_tokens: int
```

修改后代码（`engine/sequence.py` 节选）：

```python
self.request_id = str(self.seq_id)
self.arrival_time = monotonic()
self.token_timestamps = []
self.finish_time = None
self.preemption_count = 0
```

`SequenceStatus` 也增加 `CANCELLED` 和 `FAILED`；异常主要由异步 Future 传播，不能仅凭枚举存在推断所有异常都逐条设置为 `FAILED`。

**性能影响**：这是数据契约和可观测性改造，本身没有独立性能实测；它为混合调度和延迟统计提供基础。

## 3. 阶段二：增量 KV Block 分配和 Prefix Cache

**修改点与文件**：`engine/block_manager.py` 用 `attach_prefix()` 连接已有前缀块，用 `reserve()` 按本轮结束位置增量分配块；保留完整块哈希、物理块引用计数和释放逻辑。`engine/scheduler.py` 在调度前根据可用块和预算限制实际 chunk。

### 原始策略及理论

原始实现支持 Prefix Cache，但首次分配时对请求的完整当前序列分配块，即使本轮只计算其中一小段。

原始代码（`engine/block_manager.py` 节选）：

```python
num_new_blocks = seq.num_blocks
# ... 检查可复用前缀块 ...
if len(self.free_block_ids) < num_new_blocks:
    return -1

# allocate(): 为剩余完整序列分配
for i in range(num_cached_blocks, seq.num_blocks):
    seq.block_table.append(self._allocate_block())
```

假设块大小为 256、Prompt 长度为 2,048、首次只计算 512 个 token，且没有前缀命中：原始方案首次分配 8 个块，而实际本轮只需要 2 个。它实现简单，但长 Prompt 可以提前占用尚未计算的 KV 空间。

### 修改后策略及理论

本轮目标位置为 `end`，已分配逻辑块数为 `a`，块大小为 `S`，则新增块数为 `max(0, ceil(end / S) - a)`。每次只为已计划的 token 预留物理空间；完整前缀块可以由多个请求引用，引用计数归零后才能返回空闲队列。至少保留一个 token 需要实际计算，才能获得用于采样的隐藏状态。

修改后代码（`engine/block_manager.py`）：

```python
def reserve(self, seq: Sequence, end: int) -> bool:
    needed = max(0, (end + self.block_size - 1) // self.block_size
                 - len(seq.block_table))
    if needed > len(self.free_block_ids):
        return False
    for _ in range(needed):
        seq.block_table.append(self._allocate_block())
    return True
```

前缀连接代码节选：

```python
for i in range((seq.num_tokens - 1) // self.block_size):
    tokens = seq.block(i)
    h = self.compute_hash(tokens, h)
    block_id = self.hash_to_block_id.get(h)
    if block_id is None or self.blocks[block_id].token_ids != tokens:
        break
    # ... 更新引用计数和空闲/使用集合 ...
    seq.block_table.append(block_id)
    seq.num_cached_tokens += self.block_size
```

**理论性能影响**：上例首轮占用从 8 块降为 2 块，后续计算仍可能逐步占满 8 块；这只是由分配策略推导出的块数示例，不是显存峰值实测。按需分配可能让更多请求同时进入系统，但还会增加调度/分配开销；资源紧张时抢占后重算也会增加计算量。

## 4. 阶段三：统一 Token Budget、分块和混合调度

**修改点与文件**：`engine/scheduler.py` 重构调度和后处理；`config.py` 新增 `prefill_chunk_size`；`engine/scheduler_output.py` 保存逐请求调度结果。

### 原始策略及理论

原版先扫描等待队列安排 Prefill；只要选出 Prefill，立即返回，不执行 Decode 调度。预算不足时只允许第一个请求部分 Prefill。没有 Prefill 才安排 Decode，因此 Decode 不能与新 Prefill 在同一个模型批次内计算。

原始代码（`engine/scheduler.py` 节选）：

```python
if remaining < num_tokens and scheduled_seqs:
    break  # only allow chunked prefill for the first seq
seq.num_scheduled_tokens = min(num_tokens, remaining)
# ...
if scheduled_seqs:
    return scheduled_seqs, True

# 只有没有 prefill 时才进入 decode
while self.running and len(scheduled_seqs) < self.max_num_seqs:
    # ...
    seq.num_scheduled_tokens = 1
```

原策略易于维持批次同质性，但连续进入的 Prefill 会推迟正在生成的请求；原有 `max_num_batched_tokens` 并未统一约束 Prefill 和 Decode 的总计算量。

### 修改后策略及理论

一轮中各请求计算 token 总数满足 `sum(n_i) <= max_num_batched_tokens`，请求数满足 `len(scheduled) <= max_num_seqs`；Decode 通常消耗 1 个预算，Prefill 受剩余预算、`prefill_chunk_size` 和 KV 容量限制。调度器优先安排运行中的 Decode，再安排 Prefill，并通过运行队列轮转改善同类请求的机会。KV 不足且本轮无法安排工作时，选择运行队列末尾的请求抢占，释放块并在之后重算。

修改后代码（`engine/scheduler.py` 节选）：

```python
budget = self.max_num_batched_tokens
scheduled = []
candidates = sorted(self.running,
                    key=lambda s: s.num_cached_tokens < s.num_prompt_tokens)
for seq in candidates:
    if budget == 0 or len(scheduled) >= self.max_num_seqs:
        break
    decode = (seq.num_cached_tokens >= seq.num_prompt_tokens
              and seq.num_tokens - seq.num_cached_tokens == 1)
    capacity = (len(seq.block_table) + len(self.block_manager.free_block_ids)) * self.block_size - seq.num_cached_tokens
    n = min(seq.num_tokens - seq.num_cached_tokens, budget,
            1 if decode else self.chunk_size, capacity)
    if n > 0 and self.block_manager.reserve(seq, seq.num_cached_tokens + n):
        seq.num_scheduled_tokens = n
        scheduled.append(ScheduledRequest(
            seq, n, ExecutionMode.DECODE if decode else ExecutionMode.PREFILL,
            seq.num_cached_tokens + n == seq.num_tokens))
        budget -= n
```

之后的等待队列准入同样消费 `budget`，将新请求作为 Prefill 加入同一个 `scheduled`；无可调度请求时，代码尝试抢占或显式报告容量不足。运行中请求按上述排序规则选择，不能将它等同于严格的全局公平调度或强饥饿保证。

**理论性能影响**：减少 Decode 被长 Prefill 整批阻塞的机会，可能改善 ITL/TPOT；多请求共享一次 forward 可能提高设备利用率。但 chunk 过小会增加调度及 kernel 启动次数，Decode 优先也可能增加 Prefill 等待；收益依赖负载和 GPU，尚无对照实测。

## 5. 阶段四：混合批次、注意力元数据和采样

**修改点与文件**：`engine/model_runner.py` 复用变长 Prefill 路径处理包含 Prefill 的混合批次，并按请求构造采样标记；`utils/context.py` 增加 `sample_indices`；`layers/embed_head.py` 仅对需要采样的隐藏状态计算 logits；`layers/attention.py` 保留原来的两条 Attention 路径，仅修改了包导入。`layers/sampler.py` 和 `sampling_params.py` 支持 `temperature=0` 贪心采样。

### 原始策略及理论

原版 Prefill 使用变长 FlashAttention；有历史前缀时通过 block table 访问分页 KV。Decode 使用 `flash_attn_with_kvcache`，可通过 CUDA Graph 重放。原版 LM Head 在 Prefill 时选每个请求最后一个 query，对整个批次采样；原始后处理虽然不把中间 chunk 的采样结果写入序列，但仍计算了该 chunk 的 logits 和采样。

原始代码（`layers/embed_head.py`）：

```python
if context.is_prefill:
    last_indices = context.cu_seqlens_q[1:] - 1
    x = x[last_indices].contiguous()
logits = F.linear(x, self.weight)
```

原始执行入口（`engine/model_runner.py`）：

```python
input_ids, positions = self.prepare_prefill(seqs) if is_prefill else self.prepare_decode(seqs)
temperatures = self.prepare_sample(seqs) if self.rank == 0 else None
logits = self.run_model(input_ids, positions, is_prefill)
```

### 修改后策略及理论

各请求的 query 被展平成一个 token 数组。`cu_seqlens_q` 描述各请求 query 的边界，`cu_seqlens_k` 描述各请求从位置 0 到本轮结束的可见 KV 长度；`block_tables` 映射逻辑块到物理块，`slot_mapping` 指向本轮新增 KV 的物理位置。位置 `p` 的 slot 为 `block_table[p // S] * S + p % S`。

一旦批次含 Prefill，所有请求——包括同批 Decode——走变长 Attention 的 eager 路径；若已有历史 KV，Attention 使用分页缓存及 block table；没有历史 KV 时沿用直接的变长 K/V 输入。只有纯 Decode 批次可以继续使用原有 CUDA Graph（受 `enforce_eager` 等条件约束）。这依赖所安装 FlashAttention 对 paged KV 和相应因果掩码的支持，并没有新增自定义混合 Attention kernel。

修改后代码（`engine/model_runner.py` 节选）：

```python
sample_indices_list = [cu_seqlens_q[i + 1] - 1
                       for i, flag in enumerate(sample_flags or [True] * len(seqs))
                       if flag]
# ... 将列表转换为 CUDA tensor ...
set_context(True, cu_seqlens_q, cu_seqlens_k, max_seqlen_q,
            max_seqlen_k, slot_mapping, None, block_tables, sample_indices)
```

```python
input_ids, positions = (self.prepare_prefill(seqs, sample_flags)
                        if is_prefill else self.prepare_decode(seqs))
temperatures = self.prepare_sample(
    [seq for seq, flag in zip(seqs, sample_flags) if flag]
) if self.rank == 0 else None
```

修改后代码（`layers/embed_head.py`）：

```python
if context.sample_indices is not None:
    x = x[context.sample_indices].contiguous()
elif context.is_prefill:
    x = x[context.cu_seqlens_q[1:] - 1].contiguous()
logits = F.linear(x, self.weight)
```

注意这里 `is_prefill` 表示执行路径是否包含 Prefill；它并不意味着混合批次中所有请求都处于 Prefill。`sample_indices` 与 temperature 列表均按调度顺序筛选，后处理按同一顺序消费 token。

**理论性能影响**：中间 chunk 避免无用的 LM Head logits 和采样；混合批次共享 forward。但混合批次使用 eager，可能失去纯 Decode Graph 的优势，变长 Attention 和 Decode 专用 kernel 的成本也可能不同。尚未测量各项收益或损失。

## 6. 阶段五：后处理、释放及抢占恢复

**修改点与文件**：`engine/scheduler.py` 调整 `postprocess()`、新增 `cancel()`、记录抢占；`engine/sequence.py` 传输完整 token 历史，便于 TP worker 在 chunk 或抢占后取得任意切片。

### 原始策略及理论

原版根据整个批次的 `is_prefill` 决定中间 chunk 是否跳过追加 token；结束后释放 KV。原序列化协议在 Decode 时只传最后 token，减少传输数据，但不足以让远端 worker 在重算时读取任意历史切片。

原始代码（`engine/sequence.py`）：

```python
last_state = self.last_token if not self.is_prefill else self.token_ids
return (self.num_tokens, self.num_prompt_tokens, self.num_cached_tokens,
        self.num_scheduled_tokens, self.block_table, last_state)
```

### 修改后策略及理论

后处理先根据本轮已计算 token 哈希完整块并推进缓存游标，再根据 `should_sample` 消费结果。采样出的 token 在下一轮才进入 KV；正常结束与取消都释放块。抢占会释放 KV 并把请求放回等待队列，之后可复用已有前缀或重算，已生成的输出不应重复追加。

修改后代码（`engine/scheduler.py` 节选）：

```python
self.block_manager.hash_blocks(seq)
seq.num_cached_tokens += item.num_scheduled_tokens
seq.num_scheduled_tokens = 0
if not item.should_sample:
    continue
token_id = next(tokens)
seq.append_token(token_id)
seq.token_timestamps.append(monotonic())
# ... 判断 EOS / max_tokens，并在完成时释放 block ...
```

修改后序列化（`engine/sequence.py`）：

```python
def __getstate__(self):
    return self.__dict__

def __setstate__(self, state):
    self.__dict__.update(state)
```

**理论性能影响**：取消可及时释放 KV；完整历史序列化增加 TP worker 通信量；抢占能恢复调度但重算有开销。TP=2 尚无实机验证，不能据此声称多卡性能或正确性已验证。

## 7. 阶段六：异步请求与流式输出

**修改点与文件**：新增 `engine/async_llm_engine.py`；`engine/llm_engine.py` 的 `add_request()` 返回 `Sequence`，`step()` 输出 token 事件，`exit()` 可重复调用；`config.py` 增加 `max_pending_requests`；`__init__.py` 暴露异步入口。

### 原始策略及理论

原版 `generate()` 接收一批请求，在当前调用中循环 `step()`，直到整个引擎完成，最后统一返回。它支持批内连续生成，但调用方不能通过该接口独立等待每个请求或逐 token 消费。

原始代码（`engine/llm_engine.py` 节选）：

```python
for prompt, sp in zip(prompts, sampling_params):
    self.add_request(prompt, sp)
outputs = {}
while not self.is_finished():
    output, num_tokens = self.step()
    for seq_id, token_ids in output:
        outputs[seq_id] = token_ids
```

### 修改后策略及理论

`AsyncLLMEngine` 在单独线程中持有同步引擎，命令队列接收提交、取消、停止；调用方获得每请求独立 Future 与 token 队列，工作线程通过事件循环分发结果。每次仍只有一个 GPU batch 在飞：异步的是请求接收和交付，不代表 GPU 多批流水化。并发请求数达到上限时立即拒绝，而不是无限增长。

修改后代码（`engine/async_llm_engine.py` 节选）：

```python
handle = RequestHandle(request_id, self.loop.create_future(),
                       asyncio.Queue(), self, monotonic())
self.handles[request_id] = handle
handle.result_future.add_done_callback(
    lambda f: self.cancel(request_id) if f.cancelled() else None)
self.commands.put(("add", handle, prompt, sampling_params or SamplingParams()))
return handle
```

调用示例：

```python
async with AsyncLLMEngine('/path/to/Qwen3') as engine:
    handle = engine.submit('Hello', SamplingParams(temperature=0, max_tokens=32))
    async for token_id in handle.stream():
        print(token_id)
    result = await handle.result()
```

**理论性能影响**：请求提交与等待不必阻塞事件循环，结果可更早交付；它不保证单请求 GPU 执行更快。token 队列、线程调度和事件循环也有开销。现有测试使用模拟引擎检查 Future、流和取消；GPU benchmark 检查了异步并发完成，但没有单独在 GPU 上覆盖所有取消时序。

## 8. 阶段七：采样、包路径、测试和性能观测

### 采样与包路径

原始 `SamplingParams` 禁止 `temperature <= 1e-10`；修改后允许零温度并在 sampler 中选择 `argmax`，用于确定性回归。源码原先导入 `nanovllm`，修改后导入本仓库的 `wwvllm`，避免意外执行其他安装的包；这涉及多个文件的导入语句，**并不意味着每个文件的算法都改变**。

原始代码（`sampling_params.py`）：

```python
assert self.temperature > 1e-10, "greedy sampling is not permitted"
```

修改后代码（`layers/sampler.py` 节选）：

```python
greedy = logits.argmax(dim=-1)
logits = logits.float().div_(temperatures.clamp_min(1e-10).unsqueeze(dim=1))
# ... 计算随机采样结果 sample_tokens ...
return torch.where(temperatures == 0, greedy, sample_tokens)
```

| TTFT P50 / P95 | 4.445 / 4.445 s | 未测 | 无法计算 |
| TPOT P50 / P95 | 0.068 / 0.068 s | 未测 | 无法计算 |
| ITL P50 / P95 | 0.064 / 0.100 s | 未测 | 无法计算 |
| 抢占次数 | 0 | 未测 | 无法比较 |

只有两个请求，不足以可靠估计尾延迟；该值也不能作为稳定吞吐。基准脚本为 [benchmarks/online.py](../benchmarks/online.py)。

指标含义：`TTFT = 首 token 时间 - 请求提交时间`；`TPOT = (末 token 时间 - 首 token 时间) / (输出 token 数 - 1)`；`ITL` 是相邻 token 时间差；吞吐按生成的输出 token 总数除以墙钟时间，不把 Prompt token 混入输出吞吐。

### 建议的性能对照方法

1. 固定两个 Git 版本、模型权重、GPU、精度、驱动、依赖、模型长度和采样方式；记录硬件是否被其他作业占用。
2. 分别进行预热，再重复多次测量并报告每轮结果与分布。对原版离线 `generate()` 与新版离线接口先做可比吞吐测试；在线场景需要为原版提供等价负载驱动或明确其接口限制，不能把不同计时边界直接比较。
3. 测试短输入长输出、长输入短输出、混合长度、并发和 KV 压力；固定到达时间或到达率，并记录输出吞吐、TTFT、TPOT、ITL、端到端延迟、KV 峰值和抢占次数。
4. 固定其余参数，仅改变 chunk 大小、是否允许混合、是否启用增量分配等；当前实现没有完整的消融开关，需要先建立等价实验配置。使用 `(新值 - 原值) / 原值` 计算吞吐变化，延迟下降率则使用 `(原值 - 新值) / 原值`。
