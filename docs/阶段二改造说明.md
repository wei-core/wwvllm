# 阶段二：推测解码与 KV Cache 事务

## 1. 范围和前置基线

阶段一基线为 Git 提交 `e0c3da7`；阶段一说明文档提交为 `652cd62`。本文描述在该基线上新增的阶段二代码。草稿模型采用 Transformers 的 Qwen3 实现，目标模型继续使用本仓库已有模型和分页 KV。该实现首先以正确性为目标：推测模式目前只支持单 GPU、一次处理一个推测请求，草稿 KV 每轮从已提交序列重建；它不是持久化草稿缓存，也没有推测批次 CUDA Graph。

## 2. 修改总览

| 阶段 | 阶段一策略 | 阶段二修改 | 主要文件 |
| --- | --- | --- | --- |
| 采样 | temperature 和 greedy；每次一个 token | top-k、top-p；候选接受率与残差采样 | `sampling_params.py`, `layers/speculative_sampler.py`, `engine/model_runner.py` |
| KV | 按本轮终点增量分配，完成后立即有效 | 事务预留、按接受数量提交、拒绝后释放剩余块 | `engine/block_manager.py` |
| 调度 | 统一预算，Decode 一次 1 token | 新增 SPECULATIVE；验证输入 K+1 计入同一预算；资源/长度不满足则普通 Decode | `engine/scheduler.py`, `engine/scheduler_output.py` |
| 模型执行 | Prefill 变长 Attention，Decode 通过单 token 路径 | 独立 Draft 提案，Target 用变长 eager 一次返回 K+1 位置的 logits | `engine/draft_runner.py`, `engine/model_runner.py` |
| 后处理 | 一次最多追加一个 token | 接受的前缀加修正或 bonus，截断 EOS/输出长度，并推进有效 KV | `engine/scheduler.py`, `engine/llm_engine.py` |

## 3. 理论与采样代码对照

### 原始策略和代码

阶段一只使用温度缩放或 greedy；原 `Sampler.forward` 摘要如下，整个普通 Decode 每次采样一个 token：

```python
greedy = logits.argmax(dim=-1)
logits = logits.float().div_(temperatures.clamp_min(1e-10).unsqueeze(dim=1))
probs = torch.softmax(logits, dim=-1)
sample_tokens = probs.div_(torch.empty_like(probs).exponential_(1).clamp_min_(1e-10)).argmax(dim=-1)
return torch.where(temperatures == 0, greedy, sample_tokens)
```

### 修改策略和理论

候选 `y` 由 Draft 分布 `q` 提出，Target 分布为 `p`：以 `min(1, p(y)/q(y))` 的概率接受；第一次拒绝时从 `normalize(max(p-q, 0))` 中采样替代 token；全部接受时从额外一个 Target 分布采样 bonus。逐个位置停止于首次拒绝。该概率修正使单次输出边缘分布等于 Target 分布；随机模式无需与普通采样使用相同随机数或逐 token 一致。温度、top-k、top-p 都必须作用于真实的 `p` 和 `q` 后才能验证。

新代码（`layers/speculative_sampler.py` 节选）：

```python
if torch.rand((), device=p.device) >= torch.clamp(p[token] / q_token, max=1):
    residual = (p - q).clamp_min(0)
    total = residual.sum()
    if total <= 0:
        raise RuntimeError("empty residual distribution after rejection")
    return SpeculativeResult(accepted + [sample(residual / total)],
                             len(accepted), len(draft_ids))
```

贪心模式比较候选与 Target `argmax`，不一致立即返回 Target token；全部一致则取 bonus 的 `argmax`。`top_k=0` 和 `top_p=1` 分别关闭相应截断。普通模式使用同样的请求采样规则。截断排序和保留完整概率张量会增加时间及显存成本。

## 4. KV 事务与游标

### 原始策略和代码

阶段一已提供增量分配，目标结束位置确定后调用 `reserve(seq, end)`：

```python
needed = max(0, (end + self.block_size - 1) // self.block_size - len(seq.block_table))
if needed > len(self.free_block_ids):
    return False
for _ in range(needed):
    seq.block_table.append(self._allocate_block())
```

原本没有验证中间状态；Target 写出的 KV 立刻由普通后处理推进为有效范围。

### 修改策略和理论

设开始时有效 KV 为 `C`，已知序列最后一个 token 仍未计算。验证输入为 `pending token + K 个候选`，即 `K+1` 个输入。若接受 `A` 个候选，真正可提交的 KV 终点为 `C + 1 + A`；修正或 bonus token 仍等待下次前向。写过但未接受的位置通过缩短逻辑有效范围作废，多余新增块释放，已有共享前缀块的引用计数不因截断而提前释放。GPU 中无效数据不需要清零，后续写入会覆盖。

新代码（`engine/block_manager.py` 节选）：

```python
old_blocks = len(seq.block_table)
if end < seq.num_cached_tokens or not self.reserve(seq, end):
    return None
transaction = KVTransaction(seq, seq.num_cached_tokens, old_blocks, end)
seq._kv_transaction = transaction
return transaction
```

`finish_transaction()` 校验事务仍活动、提交点在预留范围内，再释放超出提交终点的新增块；`rollback_transaction()` 以旧游标作为提交终点。`hash_blocks()` 只在接受的 token 已追加到序列后执行，不对暂存候选生成可复用前缀哈希。结束时 EOS 释放整个请求的 KV。

## 5. 调度与执行

### 原始策略和代码

阶段一在 Decode 分支安排一个 token：

```python
n = min(seq.num_tokens - seq.num_cached_tokens, budget,
        1 if decode else self.chunk_size, capacity)
```

本轮 Prefill 与 Decode 可以共用总预算，混合执行时采用变长 Attention。

### 修改策略和代码

推测请求仅在处于正常 Decode、功能和请求均启用、剩余预算/空闲块/输出长度足够时启用。`K` 被这几项共同限制，预算消耗为 `K+1`，不足时回退普通 Decode：

```python
k = min(self.speculative_num_tokens, budget - 1, capacity - 1,
        remaining_output - 1)
if decode and self.enable_speculative and seq.speculative_enabled and k > 0:
    transaction = self.block_manager.begin_transaction(seq, seq.num_tokens + k)
    if transaction is not None:
        seq.num_scheduled_tokens = k + 1
        scheduled.append(ScheduledRequest(seq, k + 1,
            ExecutionMode.SPECULATIVE, True, transaction))
        budget -= k + 1
        continue
```

普通任务先按阶段一执行，推测请求再逐条执行；它们共享一次调度预算，但不在同一个 GPU forward 中混合。验证发生异常时 `LLMEngine.step()` 回滚尚未完成的事务并传播异常。`SamplingParams(speculative=False)` 可让该请求保持普通模式；也可在内部通过 scheduler 标志控制后续调度。首个输出由普通 Prefill 产生，故推测只发生在 Decode。

## 6. 独立 Draft 和 Target 验证

### 原始策略

阶段一不存在第二个模型。`ModelRunner` 将每个 Prefill 位置的最后一个隐藏状态或每个 Decode 位置送入 LM Head，一次产生一个采样结果。

### 修改策略及理论

`DraftRunner` 在同一进程中加载独立 Qwen3 模型和独立 KV，每轮从已提交的完整 token 序列重新构建自己的 KV，随后串行生成 K 个候选及对应概率；事务完成后该临时 KV 被释放。不会将候选直接写入目标 `Sequence`。该方法避免 Draft 和 Target KV 混用或跨轮同步出错，但长上下文下代价很高。

Target 使用拷贝出的临时序列拼接候选，在阶段一的分页变长路径处理 `pending + candidates`。对应 query 的每个位置输出 logits：位置 0 验证第一个候选，位置 i 验证第 i+1 个候选，最后一个位置提供 bonus。目标 KV 写入事务预留的 slot，然后根据结果提交或回滚。

代码（`engine/model_runner.py` 节选）：

```python
draft_ids, draft_probs = self.draft_runner.propose(seq, count)
verify_seq = copy(seq)
verify_seq.token_ids = seq.token_ids + draft_ids
verify_seq.num_tokens = len(verify_seq.token_ids)
verify_seq.num_scheduled_tokens = count + 1
input_ids, positions = self.prepare_prefill([verify_seq], [True])
get_context().sample_indices = torch.arange(count + 1, device="cuda")
logits = self.run_model(input_ids, positions, True)
```

Draft 与 Target 的词表映射、特殊 token ID 和词表大小必须一致，Draft 的上下文长度必须覆盖目标配置；当前配置强制 `tensor_parallel_size=1`。Target KV 分配时按 `draft_memory_reserve` 扣留额外 GPU 内存，以留给 Draft KV 和工作空间；该比例不是长期上下文下不 OOM 的保证。

## 7. 后处理、流与状态

普通路径按原样追加一个 token。推测路径先按 EOS/最大输出长度截断结果，再追加接受的候选、哈希已提交完整块、提交 KV 事务、追加修正或 bonus，并逐 token 形成事件。异步线程将这些事件按序放进请求输出队列；最后一个事件完成 Future。取消仍在模型执行的批次间处理，不是 GPU kernel 中断。

统计字段 `draft_proposed`、`draft_accepted`、`target_verifications` 在 `Sequence` 中维护，并随异步最终结果返回。`accepted/proposed` 是候选接受率，不等于吞吐提升。存在 EOS 截断时，已提交数会受截断限制。

## 8. 使用方式

```python
from wwvllm import LLM, SamplingParams

llm = LLM('/path/to/target', enable_speculative=True,
          speculative_model='/path/to/draft', speculative_num_tokens=2,
          tensor_parallel_size=1)
try:
    outputs = llm.generate(['Hello'], SamplingParams(
        temperature=0.7, top_k=50, top_p=0.9, max_tokens=64))
finally:
    llm.exit()
```

Draft 必须为 tokenizer 兼容的 Qwen3 模型。普通请求可使用 `SamplingParams(speculative=False)`；未启用推测时不加载 Draft。详细入口见 [README](../README.md)。

## 9. 验证与性能

- 采样单元测试覆盖温度/top-k/top-p、贪心接受与拒绝、强制首次和后续拒绝，以及 12,000 次随机试验与目标分布的统计对照。统计试验验证选定示例，不代替数学证明或覆盖所有浮点极端情况。
- KV 测试覆盖跨块预留、提交、回滚保护、EOS 截断及释放；调度测试检查预算、提交后的 `num_cached_tokens == num_tokens - 1` 和请求级普通模式回退。
- GPU 测试使用 Qwen3-0.6B 同时作为目标与草稿，比较普通 Decode、正常推测以及强制候选错误后的贪心输出；包含 255 token 输入以覆盖 256 块边界。阶段一 GPU 回归独立进程执行，避免 CUDA Graph 池影响后续测试显存。
- 真实模型已执行小规模随机采样烟雾测试；端到端随机分布统计、真实不同草稿模型、长压测、故障恢复和多 GPU 尚需进一步测试。随机分布的统计测试目前针对采样算法而非完整 GPU 模型。

可复现命令：

```bash

/home/ubuntu/miniconda3/envs/ai-nanovllm/bin/python -m pytest -q tests
```

一次暖机后的单请求对比见 [SPECULATIVE_RESULTS.md](../benchmarks/SPECULATIVE_RESULTS.md)：同一个 0.6B 模型作为 Target/Draft，K=2、输入 32、输出 16，普通 16.11 token/s，推测 7.31 token/s（0.454 倍），候选 10/10 接受、调度轮次 16→6。两种模式均加载草稿模型，计时为单次测量，GPU 被共享。这个实验表明本配置**没有性能提升**，不能推断其他模型和负载的效果。要识别收益，需要更小的兼容 Draft、持久草稿 KV、重复多负载对照、TTFT/TPOT/ITL 和单独峰值显存测量。
