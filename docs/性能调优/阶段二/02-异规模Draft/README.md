# 阶段二重测：同系列不同规模 Draft

## 目的和配置

[上一项实验](../01-Draft缓存/README.md)使用相同的 0.6B 模型充当 Target 和 Draft，其近 100% 的接受率及性能不代表实际小 Draft 场景。本次保持阶段二的 Target 验证、概率校正与 KV 事务实现不变，用不同参数规模重做 Draft 缓存实验，同时加入普通自回归解码作参照。

- Target：Qwen3-1.7B，BF16；Draft：Qwen3-0.6B，BF16；K=4。Qwen3-8B 的 BF16 权重本身约需 16 GB，超过本机单卡 8 GiB 显存，因此不能在本机以该示例配置运行。本实验不能代表 8B/0.6B 的结果。
- 硬件：RTX 5060 8 GiB；单 GPU，eager 模式，PyTorch 2.9.1+cu128；共享桌面显存。本次两模型和运行时占用接近显存上限，实验配置不是通用安全容量承诺。
- 1.7B 的两片权重 SHA-256 分别为 `169ad53ec313c3a34b06c0809216e4fc072cce444a5d4ff2b59690d064130ed5`、`912becff8d60672aa8628ef08c05898d9adf17c2ad4ae3caf99b065622fdeff9`，与 Hugging Face 上游修订 `70d244cc86ccca08cf5af4e1e306ecf908b1ad5e` 的元数据一致。
- tokenizer 完整词表映射、特殊 token 列表、特殊 token 映射、模型 BOS/EOS 均一致；两套 `tokenizer.json` 的 SHA-256 均为 `aeb13307a71acd8fe81861d94ad54ab689df773318809eed3cbe794b4492dae4`，`tokenizer_config.json` 均为 `d5d09f07b48c3086c508b30d1c9114bd1189145b74e982a265350c923acd8101`。配置中的 vocab_size 均为 151936，实际 tokenizer 词表映射均为 151669 项。
- 代码基线 `282ae1b`；三个实验臂均加载同一 Target 和 Draft，普通解码臂关闭推测调度，以尽量统一显存和 KV 可用量。不同进程实际分配到的 KV 块数及显存见原始数据。
- 参数：`max_num_batched_tokens=256`、`prefill_chunk_size=256`、`max_num_seqs=4`、`max_model_len=1024`、`gpu_memory_utilization=.96`、`draft_memory_reserve=.04`、temperature=0.6、ignore_eos；合成输入从 1–10000 之间生成 token ID。
- 负载：短批次 4×128→32；长批次 2×512→16；交错负载 64→64 加两个 384→16 请求。每进程每种负载预热一次后测两轮，重建/缓存进程顺序为重建、缓存、缓存、重建；普通解码只测一个进程两轮，并不属于 ABBA，受运行顺序与共享 GPU 噪声影响。相同随机种子并不保证不同解码路径输出相同 token。

缓存实验复用上一轮的候选脚本：按已提交 token 共同前缀裁剪 Draft KV，最多保留 8 条，跨负载仍会保留近期条目。它缺少生产环境请求完成/取消时的即时释放以及按字节的显存预算，本次没有合入生产。

## 正确性限制

单请求短提示 greedy 一致；单请求长提示和双请求中，普通解码与两条推测路径在相同位置发生分歧。具体 token 及执行日志见 `data/check-rebuild.log`、`data/check-cache.log`。所以本次推测性能**仅用于诊断，不能视为已满足目标模型 greedy 一致性**；需要进一步检查数值路径与 KV/验证行为。推测采样的分布一致性也未做统计检验。

每行时延是各轮对应统计值的算术平均；step 内一次发出多个 token 的时间戳相同，因此推测路径的 TPOT/ITL 为 step 粒度观测，不等于精确逐 token 的 GPU 延迟。不同路径可能生成不同 token，接受率和工作量也随之变化，不能仅归因于缓存。推测臂使用同一个输入和随机种子，但部分结果的输出哈希不同；`data/*.json` 保存完整数据。

所有进程目标 KV 均为 65 块。预热之后 PyTorch `max_memory_allocated`：普通解码 6,587,439,104 bytes；两次原始重建均为 6,690,782,208 bytes；两次缓存均为 6,946,852,864 bytes。这是进程内分配峰值，不是整卡峰值；测试中整卡占用曾接近 7.7 GiB。缓存候选因保留独立 Draft KV 增加了驻留内存。

## 分歧位置的目标 logits

`trace_logits.py` 对单条长提示复现后，在两个路径有相同的 142-token 前缀处采集 Target 输出。普通路径 token 2578 和 5646 的 BF16 logits 均为 27.25，greedy 选中 2578；推测验证路径对应值分别为 27.25、27.375，greedy 选中 5646，随后输出分歧。完整 top-5 与 token 序列在 `data/trace-logits.json`。该结果表明相同前缀的 Target 输出在两条执行路径存在可观察差异；接近并列时的 BF16 舍入和不同计算形状是可能因素，但目前不能排除 KV 或验证实现问题，也不能据此证明概率分布等价。

## 理论与结论

推测解码的理论目标是利用较小 Draft 提议 token，由 Target 批量验证并通过接受/修正保持目标分布；它没有对特定模型、硬件或实现给出固定吞吐提升。若简化假设每个提议的接受概率独立且恒为 α，K 个提议加一次 bonus 的预期提交长度约为 `1 + α + ... + α^K`。这个简化模型没有计入 Draft 前向、目标验证、调度、数据传输和请求间串行开销，不能直接套作本机加速比。相关原始方法见 [Fast Inference from Transformers via Speculative Decoding](https://arxiv.org/abs/2211.17192)。

在本次异规模 BF16 条件下，接受率明显低于同模型实验，缓存候选未显示稳定收益，且推测路径慢于普通解码；贪心检查也有未解释分歧。**不建议将缓存候选合入生产，也不能把本次结果外推到 8B/0.6B、较长生成、其他采样或其他硬件。** 下一步应先定位同前缀 Target logits 的路径差异，再分别测量 Draft 前向、Target 验证和逐请求串行调度的耗时，之后才适合针对性改造。

## 复现

模型权重不纳入 Git。将两个模型目录放到脚本默认路径后，从仓库根目录运行 `docs/性能调优/阶段二/02-异规模Draft/scripts/run.sh`；该脚本先运行两个 greedy 检查，再按固定顺序运行性能测试，正确性失败时仍继续测试并标注为诊断。`scripts/summarize.py` 汇总 JSON。单独运行 `PYTHONPATH=.. PYTHONDONTWRITEBYTECODE=1 /home/ubuntu/miniconda3/envs/ai-nanovllm/bin/python docs/性能调优/阶段二/02-异规模Draft/scripts/trace_logits.py` 可复现日志追踪；追踪会复制 GPU 张量到 CPU，不能用于性能计时。
