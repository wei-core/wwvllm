## 3. 模型注册与架构适配

### 原策略、代码与理论

原 `ModelRunner` 直接导入和构造 Qwen3：

```python
from wwvllm.models.qwen3 import Qwen3ForCausalLM
self.model = Qwen3ForCausalLM(hf_config)
```

Qwen3 Attention 的 Q/K Norm 原先通过 `if not self.qkv_bias:` 决定。QKV 是否带 bias 与是否需要 Q/K Norm 是两个不同的模型属性：Llama 常用无 bias 且无 Q/K Norm，而 Qwen3 需要 Q/K Norm。单纯复用原判断会错误地给 Llama 加归一化。

### 修改策略、代码与理论

Registry 以 `model_type` 和可选 `architectures` 选择已实现类；拒绝未知模型、非默认 RoPE 缩放、滑动窗口和非 SiLU FFN，不静默把它们当普通全注意力计算：

```python
_MODELS = {
    'qwen3': ('Qwen3ForCausalLM', Qwen3ForCausalLM),
    'llama': ('LlamaForCausalLM', LlamaForCausalLM),
    'qwen3_moe': ('Qwen3MoeForCausalLM', Qwen3MoeForCausalLM),
}
```

`Qwen3Attention` 显式区分 `use_qk_norm`、`qkv_bias`、`output_bias`。Llama 复用分页 GQA Attention、RMSNorm、RoPE 和合并 SwiGLU 计算；它关闭 Q/K Norm，并按其 `attention_bias` 设置 QKV 和输出投影 bias。Qwen3-MoE 复用 Qwen3 Attention 和缓存语义，按层配置选择 Dense MLP 或 MoE。

本阶段保留阶段二的 `sample_indices` 路径，因此推测验证可以从一次 forward 中取得多个 logits。当前 logits 索引仍由 `Context` / `ParallelLMHead` 协作处理，并未改成完全独立的 Model Adapter 接口。

**测试与影响**：真实 Qwen3 回归、小型 Llama 和 Qwen3-MoE 的 HF 逐位置 logits 对照通过；真实本地 Qwen3-MoE 检查点完成推理。Registry 本身没有单独吞吐提升实测。Llama 暂无真实大模型检查点测试，非默认 RoPE 和 Sliding Window 显式拒绝。

## 4. 权重读取与校验

### 原策略、代码与理论

原 `load_model()` 枚举 `*.safetensors`，对名字做 Q/K/V 和 Gate/Up 替换，然后调用各参数的 `weight_loader`：

```python
for file in glob(os.path.join(path, '*.safetensors')):
    with safe_open(file, 'pt', 'cpu') as f:
        for weight_name in f.keys():
            # 查找 packed_modules_mapping 并加载
```

投影合并有助于减少运行时 GEMM 数量，但没有完整性检查，缺失权重可能留下未初始化参数。

### 修改策略与代码

`SafeTensorsReader` 优先按索引 `weight_map` 打开分片，逐 tensor 读取，检查索引名与实际分片一致、重复键/重复 tensor 和缺失分片。`load_model` 只对明确的路径段做合并映射；MoE 的 `experts.*.gate_proj` 和 `up_proj` 保持独立。所有目标参数必须加载，QKV 和 Gate/Up 必须含全部子片；共享 embedding 的 `lm_head` 可按实际存储别名省略。

```python
if target not in params:
    raise ValueError(f'unexpected checkpoint tensor: {weight_name}')
if shard in loaded[target]:
    raise ValueError(f'duplicate parameter shard: {target} {shard}')
```

`layers/linear.py` 增加形状检查，避免 `copy_` 的广播掩盖错误。FP checkpoint 使用既有 TP shard loader；预量化权重当前只支持 TP=1。严格检查可能拒绝含额外权重的变体，这是有意的兼容性边界。

## 5. INT8/INT4 权重量化和 GEMM

### 原策略与理论

原并行 Linear 以 FP16/BF16 权重执行：

```python
return F.linear(x, self.weight, self.bias)
```

权重量化在每个输出通道、每个输入通道组使用 scale。对称版本近似 `w_hat = q * scale`，计算为 `y = x @ w_hat.T + b`；激活仍为 FP16/BF16。4-bit 打包一字节存两个数。理论权重节省不等于模型总显存节省：embedding、LM Head、norm、scale、zero 和 KV 均另占空间。

### 修改策略与代码

`QuantizedLinear.from_float()` 将已加载的 FP checkpoint 的 `LinearBase` 权重按组量化：INT8 取 `[-127,127]`，INT4 对称值取 `[-7,7]` 并以 zero point 8 打包。分组可包含非整除尾部；`quant_group_size` 默认 128。CPU / 非半精度 CUDA 路径使用解包反量化参考；FP16/BF16 CUDA 使用 Triton kernel，在矩阵乘中读取并反量化分组整数，累加为 FP32，不持久保存整块 FP 权重副本。

```python
scale = padded.abs().amax(-1).clamp_min(1e-8) / limit
q = (padded / scale.unsqueeze(-1)).round().clamp(-limit, limit)
# INT4: 两个 4-bit 值打包进一个 uint8
```

默认会量化已有的 `LinearBase` 投影，不量化 embedding、LM Head，也不量化 MoE 的 expert/router `nn.Linear`。这些是显式的覆盖范围而非全模型 INT4。量化发生在 FP 权重加载之后，因此初始化仍需要完整浮点模型和量化临时空间。量化 TP=1；Dense 浮点 TP 路径保留，但本机无法实测多卡。

**数值与性能**：测试将 CUDA GEMM 与同一量化权重的反量化 `F.linear` 对比，覆盖小 Decode、大 Prefill 行数以及不整除的输入维度；这衡量实现误差，不是模型量化误差。性能见第 9 节：本机单次量化权重更小，但吞吐退化；INT4 示例输出不同于 BF16。

## 6. AWQ/GPTQ 布局与加载

### 原策略和理论

阶段二不识别预量化 checkpoint。AWQ 和 GPTQ 均可能使用分组 4-bit，但打包轴和零点编码不同；把 `qweight` 当作浮点 `weight` 会得到错误结果。

### 修改策略与代码

`quantization/formats.py` 支持明确布局：AWQ GEMM 沿输出维度解包并按 `[0,4,1,5,2,6,3,7]` 重排；GPTQ 沿输入维度解包，旧版 `qzeros` 加 1，并支持 `g_idx` 分组映射。适配后统一为每输出通道的 packed INT4、scale、zero 和输入分组索引，供同一个 Triton GEMM 使用。

```python
if method == 'awq':
    q = _unpack_last(qweight, awq=True)
    z = _unpack_last(qzeros, awq=True)
elif method == 'gptq':
    q = _unpack_last(qweight.T).T
    z = _unpack_last(qzeros) + 1
```

`quantization/checkpoint.py` 读取各 projection 的 `qweight`、`qzeros`、`scales` 和可选 `g_idx`，把 Q/K/V 或 Gate/Up 按模型布局合并，检查尺寸、分组映射和剩余参数。`config.json` 中的 `quantization_config` 选择 checkpoint 后端；不能识别的位宽、AWQ 非 GEMM、缺少零点、GPTQ 非旧版编码、MoE 预量化专家或多卡量化均拒绝。

**验证边界**：对独立布局和生成的 Llama AWQ/GPTQ 小 checkpoint，结果与同一反量化权重的 HF logits 对照通过。当前没有第三方生产 AWQ/GPTQ checkpoint 的实测；不同工具的打包顺序、零点和版本不能据此假定兼容。量化 checkpoint 的未量化 embedding、head、norm 仍按严格浮点加载。

## 7. Qwen3-MoE 路由与专家执行

### 原策略与理论

阶段二只有 Dense SwiGLU：`down(SiLU(gate(x)) * up(x))`。MoE 用 Router 对每个 token 选择 top-k 个专家，执行被选 expert，并用路由权重求和。稀疏计算减少每个 token 激活的专家计算量，不自动减少全部专家权重显存。

### 修改策略与代码

`SparseMoE` 以 FP32 softmax 计算路由分数，按配置选择是否重新归一化 top-k 权重，再转回输入 dtype。`TorchMoEBackend` 按 expert 取 token，计算并 `index_add_` 聚合到原位置：

```python
weights, indices = probs.topk(self.top_k, dim=-1)
if self.norm_topk_prob:
    weights = weights / weights.sum(dim=-1, keepdim=True)
# ... 分组计算 expert 后按 token 索引加权累加 ...
```

当层索引不在 `mlp_only_layers`、专家数大于 0、且 `(layer_idx + 1) % decoder_sparse_step == 0` 时使用 MoE，否则使用 Dense MLP。Router 和每个 expert 的权重独立加载。动态 token 分组使用 PyTorch 操作，因此 `ModelRunner` 自动使用 eager，不进行 CUDA Graph capture；MoE TP=1。Backend 与 router 分离，可供后续替换。

**验证与影响**：Router 归一化开关、top-k 及分组输出与逐 token 参考实现比较通过；小型 Qwen3-MoE 的 HF logits 比较通过；真实 Huihui Qwen3-MoE 生成成功。当前使用 Python 循环和动态索引，性能较低；与不同 Dense checkpoint 的速度不构成公平架构对照。

## 9. 性能记录及限制

测试命令与原始数据见 [STAGE3_RESULTS.md](../benchmarks/STAGE3_RESULTS.md)。相同 Qwen3-0.6B、32 输入/16 输出、单请求、eager 的单次暖机结果：

| 模式 | 输出 token/s | TTFT | TPOT | 模型张量字节 |
| --- | ---: | ---: | ---: | ---: |
| BF16 | 17.77 | 0.059 s | 0.056 s | 1,213,071,360 |
| INT8 | 14.51 | 0.072 s | 0.069 s | 800,997,376 |
| INT4 | 13.76 | 0.107 s | 0.070 s | 580,796,416 |

本样本 INT8、INT4 吞吐分别低约 18.3%、22.5%；模型张量占用分别低约 34.0%、52.1%。数据来自共享 GPU、各模式一次运行，KV 容量按空闲显存自动调整，不能用这些 peak 值作严格可比显存结论。INT4 与 BF16 的输出 token 不同，不代表可忽略质量损失。

真实 Qwen3-MoE 两次测试分别为 3.42、6.22 token/s，说明单次结果波动大。单独的 instrumented 请求汇总 28 层 top-1 路由数为 `[318, 321, 341]`；该计数有同步开销，不在计时范围内。MoE 和 Dense 为不同模型，不应用数字声称二者架构性能差距。

后续应固定 GPU 负载和 KV 分配，重复 Prefill/Decode、不同 batch、不同组大小，并测量量化误差、模型质量、per-expert 负载和真实 checkpoint；当前无性能提升承诺。
